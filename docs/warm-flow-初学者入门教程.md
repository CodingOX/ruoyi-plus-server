# Warm-Flow 工作流引擎 — 初学者入门教程

## 前言：写给谁看的？

如果你：
- 听说过"工作流"但不知道具体是什么
- 被 Activiti/Flowable 的复杂度劝退过
- 项目中需要审批流程功能（请假、报销、合同审批等）
- 想知道 Warm-Flow 到底是什么、怎么用

这篇教程就是为你准备的。

---

## 第一章：工作流引擎到底是什么？

### 1.1 一个生活场景

假设公司请假流程是这样的：

```
你填单 → 主管审批 → 人事备案 → 结束
```

如果没有工作流引擎，你要自己写代码维护：
- 请假单提交后，怎么知道下一步要发给谁？
- 如果金额大于 5000 要多一步总经理审批，代码怎么改？
- 如果流程变了，是不是要改代码重新部署？

**工作流引擎就是专门解决这个问题的**——它把"流程怎么走"这件事抽象出来，变成可配置的，不需要每次改代码。

### 1.2 工作流的两个阶段

| 阶段 | 谁做 | 做什么 |
|------|------|--------|
| **设计时** | 管理员/业务人员 | 用设计器画流程图：拖拽节点、配置条件、设置审批人 |
| **运行时** | 普通用户 + 代码 | 用户提交申请、审批人处理待办、引擎自动流转 |

这两个阶段的区分是理解一切的基础。

## 第二章：Warm-Flow 是什么？

### 2.1 一句话概括

> Warm-Flow 是国产的开源工作流引擎，特点是**轻量（7 张表）、功能全面（支持所有审批操作）、集成简单（jar 包自带设计器）**。

### 2.2 和传统引擎对比

| | Activiti / Flowable | Warm-Flow |
|--|-------------------|-----------|
| 表数量 | 25+ 张 | **7 张** |
| 集成 | 复杂配置 | **加一个依赖就行** |
| 流程定义 | BPMN XML（复杂） | **JSON（直观）** |
| 设计器 | 需额外部署 | **jar 包自带** |
| 学习成本 | 高 | **低** |

### 2.3 能做什么？

- 请假审批、报销审批、合同审批等**审批流**
- 工单流转、任务追踪
- 会签（多人审批）、条件分流（金额不同走不同分支）
- 转办、委派、退回、撤销、拿回等各种审批操作

## 第三章：核心概念（7 张表对应 7 个概念）

这是最重要的章节，搞懂这些你就理解了工作流的本质。

### 3.1 流程图（你看得见的）

```
      ┌──────┐     ┌──────┐     ┌──────┐     ┌──────┐
──→   │开始   │──→  │主管审批│──→  │人事审核│──→  │结束   │
      └──────┘     └──────┘     └──────┘     └──────┘
```

### 3.2 背后的 7 张表

| 概念 | 对应表 | 大白话解释 |
|------|--------|-----------|
| **流程定义** | `flow_definition` | 画好的那张流程图模板，比如"请假流程 v1.0" |
| **流程实例** | `flow_ins` | 张三今天发起的一次请假申请（正在审批中） |
| **流程节点** | `flow_node` | 图中的每个方块：开始、主管审批、人事审核、结束 |
| **流转条件** | `flow_skip` | 节点间的箭头，可能带条件（如金额>5000才走这条线） |
| **待办任务** | `flow_task` | 现在轮到谁处理了（主管打开待办列表看到它） |
| **历史任务** | `flow_his_task` | 已经处理完的记录（张三已提交、主管已审批） |
| **历史实例** | `flow_his_ins` | 已经全部结束的流程记录 |

### 3.3 生命周期

```
管理员画图 → 发布 → 生成 flow_definition
                              ↓
用户提交申请 → 生成 flow_ins（一个流程实例）
                              ↓
生成了待办 flow_task → 审批人处理 → 完成 flow_task
                              ↓
                              ↓（循环直到结束）
                              ↓
走到结束节点 → flow_ins → flow_his_ins（归档）
```

## 第四章：审批操作术语（通过、退回、会签、转办……都是什么意思？）

> 学习提示：你在阅读 Warm-Flow 文档或使用设计器时，会频繁遇到这些术语。本章结合事例逐一讲解，帮助你一次性搞清楚。

### 一、基础操作类

#### 1. 通过

当前节点处理人对流程节点审核通过，完成后进入下一节点。

> **事例**：员工提交"差旅报销单"，部门经理作为第一审批人点击"通过"，流程自动流转到财务部审核。

#### 2. 退回

将流程驳回至之前已经处理过的任务节点，要求重新处理。

> **事例**：财务发现报销单发票不合规，点击"退回"到申请人，让他补充材料或修改金额。

退回与后面会讲的"取回"、"撤销"不同：退回是审批人主动驳回，目标通常是上一个处理节点。

#### 3. 任意跳转

处理人可自由（通过或者退回）指定到任意节点。

> **事例**：HR 在招聘流程中，觉得候选人简历没问题，想直接跳到"终面环节"跳过笔试——这就是"任意跳转到指定节点"。

这是一个高级功能，通常需要权限控制，用于灵活调整流程路径。

### 二、委托与转移类

#### 4. 委派

A 委派给 B 代办，B 审批完了，再回到 A，A 再去办理，流程才会继续流转。

> **事例**：总监出差，把"项目立项审批"委派给副总监；副总监批完后，流程回到总监这里，总监确认后再推进下一步。

要点：**责任仍在原处理人**，只是临时让别人代劳，最后还要本人收尾。

#### 5. 转办

任务直接转给其他人办理，原处理人不再参与。

> **事例**：客服收到一个技术问题工单，自己不懂，于是"转办"给技术支持团队，由他们接手处理。

> **委派 vs 转办快速区分**：
> - 委派：A → B 代审 → **回到 A** → 下一步
> - 转办：A → B 接手，A 不再管

### 三、流程干预类

#### 6. 催办

发起人提醒当前节点处理人尽快处理，一般以消息通知方式提醒。

> **事例**：合同审批卡在法务部三天没动静，销售发起人在系统里点"催办"，法务收到消息："请尽快处理 XX 合同！"

催办只起提醒作用，不影响流程逻辑。

#### 7. 取回

发起人将已经提交、但尚未被审批的流程拿回来修改。

> **事例**：员工提交了请假申请，刚提交就发现日期写错了，立刻"取回"自己的申请，改好再提交。

特点：**只能由发起人操作，且只能取回还未被审批人处理的任务**。

#### 8. 撤销

将已经被处理过的任务强制拉回来，通常需要更高权限。

> **事例**：主管已经批准了下属的加班申请，但后来发现预算超支，于是"撤销"该审批，流程退回到主管重新评估。

> **取回 vs 撤销快速区分**：
> - 取回：提交后**还没人审批**，发起人自己拿回来改
> - 撤销：**已经有人审批了**，有权限的人强制拉回来

#### 9. 终止

当前节点处理人终止整个流程，流程作废，不再流转。

> **事例**：客户突然取消订单，销售经理在审批流程中点击"终止"，整个流程作废。

### 四、协作与通知类

#### 10. 抄送

当前节点处理人处理完成后，将处理结果通知给其他人（不参与审批）。

> **事例**：行政人员批准了会议室预订，同时"抄送"给 IT 部（准备设备）、保洁部（打扫房间），让他们知情并配合。

#### 11. 加签

办理中途，希望其他人一起参与办理，增强审批安全性。

> **事例**：采购员正在审批一笔大额付款，觉得风险高，于是"加签"风控总监，让他也发表意见。

#### 12. 减签

办理中途，希望某些人不参与办理，提高效率。

> **事例**：原本需要 5 位领导签字的合同，其中一位因休假无法参与，经授权后"减签"掉他，剩下 4 人即可通过。

### 五、审批规则类

#### 13. 会签

**所有**审批人审批通过，节点才会通过（最严格模式，缺一不可）。

> **事例**：公司重大投资决策，必须 CEO、CFO、CTO、法律顾问全部同意才能生效。

#### 14. 票签

满足设定的**通过比例**即可通过，无需全员同意。

> **事例**：董事会投票表决新项目，规定"超过 2/3 成员同意即通过"，若有 9 位董事，至少 6 人同意就算通过。

#### 15. 或签

**一名**办理人审批通过，节点即通过（最快模式，适合紧急场景）。

> **事例**：紧急故障报修，只要任一值班工程师响应并处理，就算"通过"，无需等待所有人。

### 快速记忆表

| 类别 | 术语 | 一句话记忆 | 典型场景 |
|------|------|-----------|---------|
| 基础操作 | 通过 | 同意，往下走 | 正常审批 |
| | 退回 | 驳回重做 | 内容有误需修正 |
| | 任意跳转 | 自由跳到指定节点 | 流程优化、特殊审批 |
| 委托转移 | 委派 | B 代审，回到 A | 出差代理 |
| | 转办 | 完全移交 B | 专业分工 |
| 流程干预 | 催办 | 提醒加快 | 超时未处理 |
| | 取回 | 提交后没批，自己拿回 | 填错后自纠 |
| | 撤销 | 已批了，强制拉回 | 发现重大问题 |

## 第五章：设计器和运行时

### 5.1 设计器 UI 是怎么来的？

你产生过这个疑问："jar 包不是只有 Java 代码吗，怎么带界面的？"

**Warm-Flow 的做法是：把前端页面（HTML/JS/CSS）直接打包进 jar 包里。**

```
warm-flow-plugin-ui-sb-web.jar
  ├── com/.../*.class         ← 后端的 Java 代码
  └── META-INF/resources/
       └── warm-flow-ui/      ← 前端的静态资源
           ├── index.html     ← 设计器页面
           ├── js/app.js      ← Vue 打包后的 JS
           └── css/style.css  ← 样式
```

当你引入 jar 包后，Spring Boot 自动把这些静态资源暴露出来。所以你浏览器访问：

```
http://localhost:8080/warm-flow-ui/index.html
```

就能看到设计器界面。**不需要额外部署任何前端服务。**

这种方式你其实见过——Swagger 的 UI 页面也是这么干的（你访问 `/swagger-ui.html` 就能看到 API 文档页面）。

### 5.2 设计器 vs 业务系统

```
┌────────────────────────────────────────────────┐
│  后台管理系统（管理员用）                          │
│  ┌──────────────────────────────────────────┐   │
│  │  流程设计器页面                             │   │
│  │  [开始] → [主管审批] → [人事审核] → [结束]   │   │
│  │             ↑ 拖拽、配置、发布                │   │
│  └──────────────────────────────────────────┘   │
└────────────────────────────────────────────────┘
                       ↓ 发布后保存到数据库
┌────────────────────────────────────────────────┐
│  业务系统（普通用户用）                          │
│  ┌──────────────────────────────────────────┐   │
│  │  请假申请页面                              │   │
│  │  天数：[___]  原因：[___]                  │   │
│  │  [提交申请]                                │   │
│  └──────────────────────────────────────────┘   │
└────────────────────────────────────────────────┘
```

**普通用户永远看不到设计器**，他们只看到自己的业务表单。

## 第六章：节点和表单的关系

### 6.1 节点（Node）是什么？

节点是流程图里的每一个方块：`[开始]`、`[主管审批]`、`[人事审核]`、`[结束]`

### 6.2 节点 ≠ 表单

| 节点类型 | 需不需要表单 | 例子 |
|---------|------------|------|
| **人工审批节点** | **需要**（业务系统自己实现） | 主管审批页面，有"通过/退回"按钮 |
| **条件网关节点** | 不需要 | 自动判断金额走哪条路 |
| **服务任务节点** | 不需要 | 自动发邮件、调接口 |
| **开始/结束节点** | 不需要 | 流程起点和终点 |

关键理解：**Warm-Flow 管流转，不管表单渲染。** 你的每个审批页面要做成什么样，是你自己的业务系统决定的。

## 第七章：流程变量

### 7.1 流程变量就是 Map

```java
Map<String, Object> variables = new HashMap<>();
variables.put("days", 5);                     // 请假天数
variables.put("amount", 8500);                 // 金额
variables.put("department", "技术部");          // 部门
variables.put("managerId", "user_001");        // 指定审批人
```

没错，就是这么简单的一个 KV 结构。

### 7.2 流程变量的三大用途

**用途 1：条件分流**

流程图中配置条件：
```
[主管审批] ── days > 3 ──→ [总经理审批]
           ── days ≤ 3 ──→ [人事审核]
```

引擎读取变量中的 `days = 5` → 走总经理审批分支。

**用途 2：动态指定办理人**

节点配置审批人为 `${managerId}`，引擎从变量中读取 `managerId = "user_001"`，把待办分配给 user_001。

**用途 3：在监听器中执行业务逻辑**

```java
public class MyListener {
    public void afterComplete(Task task) {
        Map<String, Object> vars = task.getVariables();
        String businessId = task.getBusinessId();
        // 比如：审批通过后自动发送邮件通知
    }
}
```

### 7.3 变量的生命周期

```
启动流程时传入 variables
        ↓
伴随整个流程实例流转
        ↓
每个节点都可以读取/修改
        ↓
流程结束 → 变量归档到历史表
```

## 第八章：核心 API 调用链（最关键的一章）

### 8.1 三个核心方法

| 方法 | 谁调用 | 什么时候用 |
|------|-------|-----------|
| `startWorkflow()` | 流程**发起人** | 只启动流程，生成第一个待办，**不自动完成** |
| `startCompleteTask()` | 流程**发起人** | 启动流程 + **自动完成第一步**（最常用） |
| `completeTask()` | 各环节**审批人** | 办理自己的待办 |

### 8.2 用一张图看懂

```
完整的请假流程：
[开始] → [填申请] → [主管审批] → [人事审核] → [结束]
                          ↑
                 条件：天数>3才走人事审核
                          ↓

发起人操作：
  ① startCompleteTask()
     内部 = startWorkflow() + completeTask(填申请节点)
     ↓
     创建流程实例
     自动完成"填申请"节点（因为是自己提交的）
     生成待办给主管

主管操作：
  ② completeTask(taskId, "通过")
     ↓
     完成主管审批
     判断条件：天数=5>3 → 走人事审核
     生成待办给人审

人事操作：
  ③ completeTask(taskId, "通过")
     ↓
     到达结束节点
     流程归档
```

### 8.3 代码实现

**启动流程（发起人）：**

```java
@Service
public class LeaveService {

    @Autowired
    private WorkflowService workflowService;

    public void submitLeave(LeaveForm form) {
        // 1. 业务数据自己存
        leaveMapper.insert(form);

        // 2. 设置流程变量
        Map<String, Object> vars = new HashMap<>();
        vars.put("days", form.getDays());
        vars.put("managerId", form.getManagerId());

        // 3. 启动流程 + 自动完成第一步
        StartProcessDTO dto = new StartProcessDTO();
        dto.setBusinessId(form.getId().toString());  // 关联业务数据
        dto.setFlowCode("leave");                     // 指定用哪个流程
        dto.setVariables(vars);                       // 传入变量

        workflowService.startCompleteTask(dto);
    }
}
```

**审批待办（审批人）：**

```java
public void approve(Long taskId, String result, String comment) {
    CompleteTaskDTO dto = new CompleteTaskDTO();
    dto.setTaskId(taskId);

    // 传递审批结果
    Map<String, Object> vars = new HashMap<>();
    vars.put("approveResult", "pass");
    vars.put("comment", comment);
    dto.setVariables(vars);

    workflowService.completeTask(dto);
}
```

## 第九章：完整示例 — 请假流程实战

### 步骤 1：在设计器中画流程图

管理员访问 `http://localhost:8080/warm-flow-ui/`

拖拽节点：
```
[开始] → [填申请(自动)] → [主管审批] → [人事审核] → [结束]
```

在主管审批 → 人事审核 的连线上配置条件：
```json
{"condition": "${days > 3}"}
```

设置节点审批人：
- 主管审批节点：`${managerId}`（流程变量指定）
- 人事审核节点：固定角色 `hr_role`

点击「发布」，流程定义入库。

### 步骤 2：发起请假申请

```java
// 用户在前端填表，点提交
Map<String, Object> vars = new HashMap<>();
vars.put("days", 5);
vars.put("managerId", "user_002");  // 主管的用户 ID

StartProcessDTO dto = new StartProcessDTO();
dto.setFlowCode("leave");
dto.setBusinessId("2024001");
dto.setVariables(vars);

workflowService.startCompleteTask(dto);
```

### 步骤 3：主管审批

主管登录系统，看到待办列表：

```java
// 查询某个人的待办
List<Task> tasks = workflowService.findTasksByUserId("user_002");
```

主管打开待办，选择"通过"：

```java
CompleteTaskDTO dto = new CompleteTaskDTO();
dto.setTaskId(task.getId());
dto.setVariable("comment", "同意");
workflowService.completeTask(dto);
```

引擎自动判断 `days > 3`，走人事审核分支，生成待办给人审。

### 步骤 4：人事审核

人事登录看到待办：

```java
List<Task> tasks = workflowService.findTasksByRole("hr_role");
```

人事点"通过"：

```java
workflowService.completeTask(dto);
```

流程到达结束节点，自动归档。

## 第十章：常见理解误区

### ❌ 误区 1："工作流引擎自动帮我生成了表单页面"
**不是。** Warm-Flow 只管流程流转，你的业务表单要自己开发。

### ❌ 误区 2："流程变了就要改代码"
**不需要。** 流程变化只需要管理员用设计器重新画图发布，代码不用改。

### ❌ 误区 3："startCompleteTask 完成了整个流程"
**不是。** 它只是"启动 + 完成第一步"，后面的节点仍需逐个调用 `completeTask`。

### ❌ 误区 4："流程变量只能存字符串"
**可以存任何对象。** `Map<String, Object>` 中的 value 可以是数字、布尔值、甚至自定义对象。
